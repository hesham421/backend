## USER STORIES

---

US-FILE-001
  Story    : Consuming modules need to upload binary files (attachments,
             documents, images) to a central store on behalf of their own
             entities, and receive a stable identifier back for future
             retrieval.
  Priority : —
  Success metric : —
  Source   : module-registry-FILE.md §ENTITIES OWNED (FileDocument —
             Foundation provider; consumed by all 3.x modules, Notification,
             Audit); business-policies-FILE.md §Platform Integration Notes
             (direct @Service injection from every consuming module)
  Status   : DRAFT

---

US-FILE-002
  Story    : A frontend or mobile client needs to download a file via a
             secure, time-limited link — without requiring the Authorization
             header or exposing the file's storage location directly.
  Priority : —
  Success metric : —
  Source   : business-policies-FILE.md POLICY-CLI-02 (Encrypted Token,
             TTL 100 min, URL-embedded, action-matched) + POLICY-CLI-03
             (token generated by File Service and returned to caller before
             the actual operation)
  Status   : DRAFT

---

US-FILE-003
  Story    : A frontend or mobile client needs to upload a file via a
             secure, time-limited link — obtaining a token first from File
             Service, then using it for the actual upload operation.
  Priority : —
  Success metric : —
  Source   : business-policies-FILE.md POLICY-CLI-03 (dedicated
             token-issuing endpoint; token returned to caller before actual
             file operation; caller does not construct its own token)
  Status   : DRAFT

---

US-FILE-004
  Story    : An authorized actor (the file's owning entity or an Admin)
             needs to permanently delete a file, with confidence that the
             operation is irreversible and that unauthorized deletion
             attempts from unrelated entities or modules will be rejected.
  Priority : —
  Success metric : —
  Source   : business-policies-FILE.md POLICY-CLI-04 (deletion is final —
             no Recycle Bin in Phase 1; owner or Admin only; 403 on
             unauthorized attempt)
  Status   : DRAFT

---

US-FILE-005
  Story    : A consuming module needs to organize the files it uploads into
             named categories (e.g., "attachment," "report," "notification
             template") using a scheme it controls independently, without
             requiring any change to the File Service itself.
  Priority : —
  Success metric : —
  Source   : module-registry-FILE.md §LOVs OWNED (FileCategory — Reference
             Table, module_code-scoped, extensible by Admin; each consuming
             module seeds its own rows); §AUTO-DECISIONS (owner_type
             free-text convention — adding a new entity type must never
             require touching File Service's own registry rows)
  Status   : DRAFT

---

US-FILE-006
  Story    : The platform needs to ensure that uploaded files meet size and
             type safety constraints, so that oversized content is rejected
             at both the transport and business levels, and file type is
             validated from content rather than from a client-supplied claim.
  Priority : —
  Success metric : —
  Source   : business-policies-FILE.md POLICY-CLI-01 (10 MB transport limit
             / 5 MB content limit, independently enforced; per-category
             override via FileCategory.max_size_bytes) + POLICY-CLI-05
             (MIME type detected server-side from file content; client
             Content-Type header never trusted for validation decisions)
  Status   : DRAFT

---

US-FILE-007
  Story    : The system needs to retain a file's metadata and audit trail
             even after its binary content has been purged, so that a
             historical record of what existed is preserved for governance
             and traceability purposes.
  Priority : —
  Success metric : —
  Source   : module-registry-FILE.md §ENTITIES OWNED — Note on FileDocument
             Status Lifecycle: "DELETED status exists for records whose
             binary content has been purged but whose metadata/audit trail
             is retained"; FileStatus LOV (ACTIVE, ARCHIVED, DELETED —
             >2 states, Status Lifecycle per platform-standards.md §C.1)
  Status   : DRAFT

---

US-FILE-008
  Story    : An Admin needs to manage the file category catalogue — adding,
             modifying, or disabling categories as business modules evolve —
             without requiring a code change or redeployment.
  Priority : —
  Success metric : —
  Source   : module-registry-FILE.md §AUTO-DECISIONS (FileCategory is a
             Reference Table, module_code-scoped, extensible by Admin);
             business-policies-FILE.md POLICY-CLI-01 (per-category
             max_size_bytes override via FileCategory)
  Status   : DRAFT

---
