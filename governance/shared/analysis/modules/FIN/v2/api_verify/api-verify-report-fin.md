## 6. التنظيف · Teardown (stage F)

`cleanup()` runs in `finally`, in reverse dependency order, and touches only ids this run created. ## 8. فجوات التوثيق · Documentation gaps flagged during translation

1. `Page<T>` (index.md → Pagination Envelope) documents no `content` field. The script reads search rows from `content` (the profile's paging convention) and asserts only documented page fields (`totalElements`, `number`, `size`).
2. The error envelope is documented as `error.code / error.message / error.fieldErrors[]`, not as the profile's `{code, messageAr, messageEn}`; there is one message per response. The script asserts `error.message` presence in the language it requests (`Accept-Language: ar`, the primary language) and records the text as an observation.
3. FIN-409-UNBALANCED, FIN-409-NOT-POSTABLE-ACCOUNT, FIN-409-INVALID-DIMENSION and FIN-409-PERIOD-NOT-OPEN are documented as surfacing "as a `fieldErrors[]` entry" on several endpoints, without stating what the top-level `error.code` is then. The script accepts the code in either slot and records which slot answered — for API-FIN-020 the consumer "branches on the full error code", so a retry code that arrives only in `fieldErrors[]` would be a contract problem.
4. Known Error Codes: FIN-409-NOT-POSTABLE-ACCOUNT, FIN-409-UNBALANCED and FIN-403-SOD-VIOLATION have empty `Status` / `HTTP Status` cells (the consumer notes say 409); FIN-409-NOT-POSTABLE-ACCOUNT reads "Raised by: 1 endpoint(s)" while its note lists four APIs.
5. API-FIN-020's Business Responses omit FIN-409-NOT-POSTABLE-ACCOUNT and FIN-409-INVALID-DIMENSION, which the catalog notes attribute to API-FIN-020 and the manifest asserts on the event path (TC-FIN-100, TC-FIN-101, TC-FIN-118).
6. The API-FIN-011 request example is not a valid request: it pairs CONSTANT with `accountBusinessFieldCode` (RULE-FIN-019) and a CONSTANT dimension tag with `businessFieldCode` (RULE-FIN-026). The script builds each shape from the field descriptions ("CONSTANT only" / "MAPPING only" / "BUSINESS_FIELD only").
7. Request and response examples render string-typed codes as JSON numbers (`"code": 1101`, `"code": 2026`, `"accountDerivationValue": 1101`, `"accountCode": 1101`); the field tables type them `string`. The script sends strings and compares codes as strings.
8. Examples carry literal FK ids (`parentAccountId: 10`, `accountId: 12`, `dimensionId: 1`, `dimensionValueId: 5 / 7`, `sourceAccountId: 31`, `targetAccountId: 21 / 22`, `fiscalYearId: 1`, `periodId: 1`); the script threads real ids instead.
9. API-FIN-014 and API-FIN-017 take no body: the date by which they pick a period (`resolvePeriodContaining`) is not documented.
10. API-FIN-020 `amounts` has no documented key set or example; the script keys it by the FIELD source value `netAmount` (API-FIN-011 example) with the documented `baseAmount` example 1000.0.
11. The SEC login request and response bodies are not in FIN's api-docs; the login body keys and token keys are marked placeholders.
12. `POST /api/v1/fin/fiscal-years/search` is served without a contract id (index.md → Drift); the script cites it by path.
13. Codes, event-type rules and event references are unique on ALL rows and FIN has no activate endpoint, so verbatim example codes collide with existing data and with every rerun. The script appends a run tag to unique-keyed example values (fiscal-year code ≤ 10 characters), and takes the rule's event type as an argument: one rule per event type, ever.
14. No uniqueness is documented on fiscal-year dates. Event, template and allocation runs resolve a period by date; when another year already covers the run's dates, which period answers is not documented — pass --year-start/--year-end.
15. Lookup value lists are not published in the api-docs; the script uses only values seen in the inputs (ASSET, DEBIT, CREDIT, MANUAL, CONSTANT, MAPPING, DIRECT, BUSINESS_FIELD, FIELD, FIXED, PERCENTAGE, REMAINDER, RECURRING, MONTHLY, PAYMENT_METHOD, BRANCH_CODE, CHEQUE, CASH, OPEN, SOFT_CLOSE, HARD_CLOSE).

## 9. التشغيل · How to run

```
python api-verify-fin.py --username <user> --password <pass>             # Dev/Test, localhost:7272
  [--base-url http://localhost:<port>] [--allow-nonlocal <env name>]     # non-local targets need the flag
  [--token <jwt>] [--login-body '<json>']                                # SEC login body is undocumented here
  [--event-type <ACCOUNTING_EVENT_TYPE with no rule yet>]                # default SALES_INVOICE (example)
  [--year-start 2026-01-01 --year-end 2026-12-31 --period-count 12]     # api-docs example year
  [--uncovered-date <a date no period covers>]                           # TC-FIN-126
  [--limited-username <u> --limited-password <p> | --limited-token <jwt>] # TC-FIN-038, TC-FIN-052
  [--with-year-end] [--db-opt-in] [--log-file <backend log>] [--report <path>]
```

Preconditions the script cannot create (manifest steps 0–1): FIN's MDL lookup keys including the v2 BLOCK 8 values (CHEQUE in PAYMENT_METHOD, DIRECT retired, FIN_EVENT_BUSINESS_FIELD, FIN_DIMENSION_VALUE_SOURCE) and host values (the chosen ACCOUNTING_EVENT_TYPE, CASH); SEC registration of FIN's screens/actions with the calling role granted every FIN permission, the three FIN_ACCOUNT_MAPPINGS actions included; the seeded retained-earnings account for `--with-year-end`. `preflight()` stops the run on 401/403 before any row is written.
