I've written P2 (Database) for FIN v2, and `gov.py analyze -m FIN -v 2 --scope stage:P2` comes back CLEAN: 0 critical, 0 major, 0 minor. The checks actually covered everything: 165 field ids, 2 cross-module ids, 167 registry ids and all 16 entities.

**What changed (a migration on top of v1):**
- **Two new tables:**
  - `FIN_ACCOUNT_MAPPING` (fields DBF-FIN-149…158) stores the account mappings. Only one mapping per (event type, business field, value) can be active; a partial unique index enforces that, so a deactivated mapping doesn't block its replacement.
  - `FIN_RULE_LINE_DIM` (DBF-FIN-159…165) stores the dimension tags on rule lines, with at most one tag per dimension on a line.
  - Each new table gets its own `SEQ_*` sequence and a plain `BIGINT` primary key, following the profile's sequence rule.
- **`FIN_RULE_LINE`:** adds `account_business_field_code` (DBF-FIN-148), and `account_derivation_value` can now be NULL. A new CHECK requires exactly one of those two columns to be filled. The CHECK doesn't list any lookup codes, keeping v1's rule that allowed values live in MDL. Every existing v1 row already passes it.
- **Modified ids:** DBF-FIN-041 (trace to REQ-FIN-072 only; the existing unique constraint on `event_reference` is now the one the duplicate-event error is mapped from), DBF-FIN-101, DBF-FIN-102, and XM-FIN-001, whose read of MDL now also covers the 6 new lookup-backed columns and 15 keys. No new cross-module dependency was needed.
- **Lookup seeding into MDL's tables:**
  - adds the lookup types `FIN_EVENT_BUSINESS_FIELD` (4 values) and `FIN_DIMENSION_VALUE_SOURCE` (2 values)
  - adds `CHEQUE` to `PAYMENT_METHOD`
  - deactivates `DIRECT`, rather than deleting it.

  Every statement checks for an existing row first, so it can run before or after FIN's API onboarding without clashing.
