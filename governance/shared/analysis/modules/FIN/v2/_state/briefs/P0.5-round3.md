This engine restates what the previous stage established about a module — its scope,
its policies, its priorities — as a set of clear, traceable **user stories**. A user
story is a NEED, never a RULE. If a story reads like an enforceable rule ("the system
shall reject any submission where X"), soften it back to intent ("the requester needs
to know the submission will not go through if X") and let `P1` decide the rule.

Completion (write → registry → analyze → commit → gate) is owned by the orchestrator —
see `shared/GOVERNANCE-CORE.md`. **Delta mode is active (v2)**: read
`_state/current-{artifact}` of the previous version for every input and for this
stage's own artifact, and emit only ADDED / MODIFIED / REMOVED stories plus the
`change-manifest.md` per `shared/VERSIONING.md`.

Language policy: narrative in `ar`; story titles carry all of `ar, en`.

## 2 — User story record (`US` — mandatory format)

```
US-[MOD]-[SEQ]
  Title          : [short name — in each of ar/en]
  Story          : As a [role], I need [capability], so that [outcome]   — a NEED
  Priority       : HIGH / MEDIUM / LOW — only if stated or clearly implied; otherwise "—"
  Success metric : only if stated; otherwise "—"
  Traces         : POL-[MOD]-[SEQ] [, …]   — the policies this story serves
  Source         : [document § / quote]   — MANDATORY, no exceptions
  Status         : DRAFT → APPROVED (by the PRD approval gate)
```

```
MANDATORY SOURCING RULE
  A story with no Source is a contract violation. Do not write one "to be thorough":
  an untraceable story looks governed when it is not.
TRACES RULE
  A story that serves no policy carries "Traces: — (scope only)" and cites the
  platform summary or module registry line that motivates it. `gov.py analyze`
  reports dangling POL references.
SEQUENCE RULE
  Continuous per module, never reused; a re-run continues from the highest existing
  sequence; an APPROVED story is never edited in place — amend via a new story.
```

## 3 — Extraction rules

```
FROM the business policies
  every policy → at least one story that expresses the NEED behind it (Traces: that policy)
  stated priorities and success criteria → Priority / Success metric
FROM the module registry
  each entity owned → "the [role] needs to manage [entity]" is a legitimate seed
  lookups owned / consumed, dependencies → integration needs — only when explicit
FROM the platform summary
  tier / dependency classification → cross-module needs — only if stated, never inferred
FROM the domain-profile
  scope statements → what NOT to write; vocabulary → use verbatim

DO NOT EXTRACT
  validation rules, data constraints, API shapes, permission matrices — those are
  P1 outputs. If a policy already states a mechanism, restate it at NEED level.
  Stories for entities or capabilities the inputs never mention.
```

## 4 — Questions (allowed — for the last time in the pipeline)

```
A QUESTION exists only when the inputs leave a story's scope, priority or role
genuinely ambiguous. It is never a request for a rule or a mechanism.

QUESTION — [point]
  Affects       : US candidates [list] / scope
  Options       : A) … (trade-off)   B) … (trade-off)
  Researched    : [what the knowledge sources say — cited: profiles/erp/knowledge/erp-domain-standards.md]
  Recommended   : [option] — because [rationale]
```

Lane `analysis-dialogue`: the implementers (claude:opus, claude:sonnet) converge on each QUESTION —
challenge, answer, ≤ 4 rounds, until **mutually-acceptable** — and the converged
recommendation is presented to the user, who confirms or adjusts.

```
Resolutions are recorded in the RESOLVED DECISIONS table of the PRD. No external
open-questions file. Because no later stage may ask, every question MUST be closed
before the approval gate: an item the user will not decide is written as a story
with Status DEFERRED and an explicit "out of scope for v2" note — never left open.
```

POL-FIN-021 — لا رمز حساب في حمولة الحدث / No account code in the event payload
  Statement : [en] The system shall derive every account of a journal entry built from a canonical accounting event without reading an account code from the event payload.
              [ar] يجب على النظام أن يشتق كل حساب في قيد اليومية المبني من حدث محاسبي قياسي دون قراءة أي رمز حساب من حمولة الحدث.
  Pattern   : ubiquitous
  Trigger   : Post (event)
  Rationale : الحدث يصرّح بواقعة تجارية وFIN وحدها تقرر معناها المحاسبي
  Source    : change manifest FIN v2 — الحد الحاكم + acceptance 1؛ domain-profile G6؛ يطبّق POL-FIN-014 وPOL-FIN-020
              على اشتقاق الحساب ويحقّق استثناء النطاق في v1 "Account numbers in event payloads — never"
  Status    : CONFIRMED

POL-FIN-022 — اشتقاق الحساب بالربط / Account derivation by mapping
  Statement : [en] When a rule line derives its account by mapping, the system shall resolve the account from the value of the named business field in the event through the FIN account mapping store for that event type.
              [ar] عندما يشتق سطر القاعدة حسابه بالربط، يجب على النظام أن يحدد الحساب من قيمة الحقل التجاري المسمّى في الحدث عبر مخزن ربط الحسابات في FIN لنوع الحدث ذاك.
  Pattern   : event
  Trigger   : Post (event)
  Rationale : النقد مقابل البنك حسب طريقة الدفع (11 من 16 فرعًا قديمًا) والحساب حسب نوع المصروف
  Source    : change manifest FIN v2 §1، acceptance 1
  Status    : CONFIRMED

POL-FIN-023 — التحقق من الحساب المُشتق بالربط / Mapped account validated like a constant one
  Statement : [en] When an account is resolved through the account mapping store, the system shall validate it as a leaf, active and postable account exactly as it validates an account given as a constant.
              [ar] عندما يُحدَّد حساب عبر مخزن ربط الحسابات، يجب على النظام أن يتحقق من أنه حساب ورقي ونشط وقابل للترحيل بالطريقة نفسها التي يتحقق بها من الحساب المُعطى كقيمة ثابتة.
  Pattern   : event
  Trigger   : Post (event)
  Rationale : المسار الجديد لا يفتح ثغرة في تحقق شجرة الحسابات
  Source    : change manifest FIN v2 §1؛ يطبّق POL-FIN-003 على الحساب المُشتق بالربط
  Status    : CONFIRMED

POL-FIN-024 — رفض القيمة غير المربوطة / Unmapped business value rejected
  Statement : [en] If the business value carried by the event has no active account mapping for that event type and business field, then the system shall reject the event with a dedicated unmapped-value error and post no journal entry.
              [ar] إذا لم يكن للقيمة التجارية التي يحملها الحدث ربط حساب نشط لنوع الحدث والحقل التجاري ذاتهما، فعندئذٍ يجب على النظام أن يرفض الحدث بخطأ مخصّص للقيمة غير المربوطة وألّا يرحّل أي قيد يومية.
  Pattern   : unwanted
  Trigger   : Post (event)
  Rationale : لا قيمة افتراضية ولا تخمين أبدًا؛ السلوك الافتراضي في النظام القديم (نقد ما لم يكن شيكًا) يصبح صف ربط
              صريحًا لكل قيمة طريقة دفع، يُعبَّأ ضمن بيانات الترحيل
  Source    : change manifest FIN v2 §1، acceptance 2
  Status    : CONFIRMED

POL-FIN-025 — الروابط بيانات لا شيفرة / Account mappings are data, not code
  Statement : [en] The system shall let authorised users add, change and deactivate account mappings as FIN-owned data through a FIN screen, without any code change.
              [ar] يجب على النظام أن يتيح للمستخدمين المخوَّلين إضافة روابط الحسابات وتعديلها وإيقافها كبيانات مملوكة لـ FIN عبر شاشة في FIN، دون أي تعديل في الشيفرة.
  Pattern   : ubiquitous
  Trigger   : Create / Update / Deactivate
  Rationale : كل ما يمكن أن يتغير بيانات مُعرَّفة، كسائر إعدادات FIN
  Source    : change manifest FIN v2 §1، acceptance 3؛ domain-profile G1
  Status    : CONFIRMED

POL-FIN-026 — وسوم الأبعاد على سطور القاعدة / Dimension tags on rule-driven lines
  Statement : [en] Where a rule line declares a value for a dimension, the system shall set that dimension on the journal line it builds from the rule's constant value or from the value of the named business field in the event.
              [ar] حيثما يصرّح سطر القاعدة بقيمة لبُعد ما، يجب على النظام أن يضبط ذلك البُعد على سطر القيد الذي يبنيه من القيمة الثابتة في القاعدة أو من قيمة الحقل التجاري المسمّى في الحدث.
  Pattern   : optional
  Trigger   : Post (event)
  Rationale : النظام القديم يختم المؤسسة والفرع على كل قيد؛ بدونها تفشل المقارنة المتوازية وتفرغ تقارير الأبعاد
  Source    : change manifest FIN v2 §2، acceptance 4
  Status    : CONFIRMED

POL-FIN-027 — التحقق من قيم الأبعاد المشتقة / Event-derived dimension values validated
  Statement : [en] When a dimension value is resolved for a journal line built from an event, the system shall validate that the value belongs to that dimension and is active, applying the same dimension rules as for a manually built line.
              [ar] عندما تُحدَّد قيمة بُعد لسطر قيد مبني من حدث، يجب على النظام أن يتحقق من أن القيمة تنتمي إلى ذلك البُعد وأنها نشطة، مطبّقًا قواعد الأبعاد نفسها المطبّقة على السطر المُدخل يدويًا.
  Pattern   : event
  Trigger   : Post (event)
  Rationale : تحقق الأبعاد القائم لا يُتجاوز
  Source    : change manifest FIN v2 §2؛ يمدّ POL-FIN-011 (الأبعاد جزء من هوية الترحيل) إلى السطور المبنية من الأحداث
  Status    : CONFIRMED

POL-FIN-028 — رفض قيمة البُعد غير القابلة للتحديد / Unresolvable dimension value rejected
  Statement : [en] If a dimension value declared by a rule line is missing from the event or fails dimension validation, then the system shall reject the event and post no journal entry.
              [ar] إذا كانت قيمة البُعد التي يصرّح بها سطر القاعدة غائبة عن الحدث أو فشلت في التحقق، فعندئذٍ يجب على النظام أن يرفض الحدث وألّا يرحّل أي قيد يومية.
  Pattern   : unwanted
  Trigger   : Post (event)
  Rationale : القيد بلا إسناد فرع يُفسد المقارنة المتوازية كما يفسدها الحساب الخاطئ
  Source    : change manifest FIN v2 §2 "using the same discipline as accounts" و"the existing validation is not

POL-FIN-029 — شكل أبعاد موحّد / One dimension shape for all lines
  Statement : [en] The system shall record the dimension values of event-built journal lines in the same form as those of manually built journal lines, so that ledger and dimension reports treat both identically.
              [ar] يجب على النظام أن يسجّل قيم الأبعاد لسطور القيد المبنية من الأحداث بالشكل نفسه المستخدم لسطور القيد المُدخلة يدويًا، بحيث تعاملها تقارير الأستاذ والأبعاد معاملة واحدة.
  Pattern   : ubiquitous
  Trigger   : Post (event)

  Source    : change manifest FIN v2 §2

POL-FIN-030 — خطأ الحدث المكرر دائمًا / Duplicate event always answered as duplicate
  Statement : [en] If a canonical accounting event arrives with an event reference that is already recorded, then the system shall answer the duplicate-event error whether the duplicate is detected by the pre-check or by the uniqueness guarantee of the store.
              [ar] إذا وصل حدث محاسبي قياسي بمرجع حدث مسجَّل مسبقًا، فعندئذٍ يجب على النظام أن يجيب بخطأ الحدث المكرر سواء اكتُشف التكرار بالفحص المسبق أو بضمان التفرّد في المخزن.
  Pattern   : unwanted
  Trigger   : Post (event)

  Status    : CONFIRMED

POL-FIN-031 — رمز مميز لرفض الفترة غير المفتوحة / Distinct code for a non-open period

              [ar] إذا استهدف ترحيل حدث فترة محاسبية غير مفتوحة للترحيل، فعندئذٍ يجب على النظام أن يرفضه برمز خطأ مميز ومفهرس وموثَّق للفترة غير المفتوحة، منفصل عن كل أخطاء التحقق والإعداد.
  Pattern   : unwanted
  Trigger   : Post (event)
  Rationale : الفترة المغلقة حالة تشغيلية تزول بفتح الفترة؛ على المستهلك الانتظار وإعادة المحاولة لا وسم الحدث فاشلًا. تاريخ بلا فترة معرَّفة أصلًا خطأ إعداد منفصل، لا يُعالَج بإعادة المحاولة
  Source    : change manifest FIN v2 §4، acceptance 6؛ resolved decision v2-5؛ يحدّد جواب بوابة الفترة التي يفرضها POL-FIN-004
  Status    : CONFIRMED

POL-FIN-032 — ثوابت v1 على المسار الجديد / v1 invariants hold on the new path

  Pattern   : ubiquitous

  Rationale : ثوابت v1 موروثة ولا يُعاد فتحها

# CHANGE MANIFEST — CS-FIN-001
Module       : FIN      Version: v2      Baseline: v1
Change type  : ADDITIVE
Summary      : Make FIN able to derive and post a journal entry from a business event emitted by the legacy Oracle system, so that legacy accounting can be retired. Four deltas on v1, none of which reopens a v1 invariant. (1) MAPPING account derivation: a FIN-owned, screen-managed mapping store that turns a business value carried by the event into an account code, replacing the unimplemented MAPPING mode; an unmapped value is a hard error and the entry does not post. (2) Dimension tags on rule-driven lines: a rule line carries dimension values derived from the event, each either a constant or a named business field, validated by FIN's existing dimension rules, so event-built and manually-built lines have the same dimension shape. (3) A duplicate event reference must always answer the duplicate-event error, whether the pre-check or the unique constraint caught it. (4) A posting attempt into a non-open period must answer its own distinct, catalogued and documented error code. The governing boundary for all four: no account code and no accounting concept of any kind may travel inside an event payload; the event states a business fact and FIN alone decides what it means in accounting terms.

## Scope detail (the raised request, restated for this change set)

### 1. MAPPING account derivation — blocking

A rule line derives its account today by CONSTANT (the value is the account code, fixed per line) or
by DIRECT (the value names an event field carrying the account code). MAPPING is declared but throws
an unsupported error. CONSTANT cannot vary; DIRECT breaks the boundary because it puts an account
code in the payload. Two legacy behaviours choose the account by a business value and fit neither:

- Cash versus bank. Legacy posts to the cash account and swaps it for the bank account when the
  payment was by cheque. The event carries the payment method as a business fact and FIN must decide
  which account that means. Eleven of the sixteen live legacy branches need this.
- Expense account per expense type. The event carries an expense type code and the account depends
  on it.

Requested: a FIN-owned mapping store, managed as data through a FIN screen like every other
configuration in the module, holding per entry the event type it serves, the business field being
mapped (payment method, expense type code), the business source value, the account code it resolves
to, an active flag and audit fields per FIN's existing conventions. Behaviour: when a rule line's
derivation is MAPPING, the engine reads the named business field from the event, resolves it through
the store, and validates the resulting account exactly as it validates a CONSTANT one — leaf, active,
postable. An unmapped value is an error and no entry posts; never a default, never a guess. A
dedicated error code is needed and FIN's analysis owns its name.

Also to settle in this change set: DIRECT is the only remaining way an account code can enter through
a payload, and once MAPPING exists it has no legitimate use in this architecture. Review it
explicitly and record the decision as an ADR — remove, deprecate, or restrict. Leaving it unexamined
is not acceptable.

### 2. Dimension tags on rule-driven lines — blocking

FIN v1 has dimensions on the chart of accounts and reports by dimension, but lines built by the rules
engine from an event carry no dimension values at all. Legacy stamps organisation and branch on every
journal entry. Without an equivalent, every event-sourced entry loses its branch and organisation
attribution, the parallel-run comparison between legacy and FIN diverges on every row (which makes
shadow-mode verification worthless), and FIN's own dimension reports are empty for exactly the
entries that matter most.

Requested: a rule line must be able to carry dimension values derived from the event, using the same
discipline as accounts — per dimension the value is either a constant or the content of a named
business field in the event (organisation code, branch code). The resolved value is validated against
FIN's existing dimension rules (belongs to that dimension, active); the existing validation is not
bypassed. Event-built and manually-built lines must end up with the same dimension shape so that
ledger and dimension reports treat them identically.

### 3. Return the duplicate-event error reliably — small

FIN checks the event reference for a duplicate and then inserts: check-then-act. When the same event
arrives twice at once the unique constraint catches the second, but it surfaces as a generic
data-integrity failure in the 500 class rather than as the duplicate-event error. For the consumer a
duplicate is success, not failure — it means the event was already posted and the message can be
acknowledged. A generic 500 looks like an outage: the consumer retries, the message lands in the
dead-letter queue, and someone reconciles by hand an event that posted correctly the first time.

Requested: a duplicate event reference must always answer the duplicate-event error, whether it was
caught by the pre-check or by the unique constraint.

### 4. Confirm the closed-period response — small

The consumer must treat "the period is closed" differently from every other rejection: it is an
operational state that resolves itself when someone opens the period, so the event should wait and be
retried rather than be marked failed.

Requested: confirm FIN answers a posting attempt into a non-open period with its own distinct,
catalogued error code, distinct from validation and configuration errors, and that the code is
documented for the consumer to depend on. If it does not exist, add it.

## Acceptance for this change set

1. A rule line resolves its account from a business value in the event, with no account code anywhere
   in the payload.
2. An unmapped business value produces a clear error and no posted entry.
3. Mappings are added and changed as data through a FIN screen, never in code.
4. Rule-driven lines carry validated dimension values derived from event fields.
5. A duplicate event reference always answers the duplicate-event error.
6. A closed-period rejection has its own distinct, documented code.
7. Every FIN v1 invariant still holds for entries produced through the new path — debits equal
   credits, leaf and active accounts only, the period gate at post time, positive amounts with
   direction, the single remainder line, duplicate rejection, derived balances, immutable audit
   trail. These are inherited, not reopened.

## Out of scope for this change set

- The in-database queue, the consumer service, and everything inside the legacy Oracle system.
- Seeding the actual account mappings for the migration: that is migration data, produced once the
  mapping store exists.
- A second event source or a broker: the consumer is built so adding one later is an added adapter,
  not a rebuild.
- The v1 exclusions stand unchanged — multi-currency, multi-ledger and multi-entity, intercompany,
  statistical accounts, multi-pattern calendar, attachments.
- The machine-caller authentication needed by the consumer is a SEC delta, tracked separately, not
  part of this change set.

## §1 Module tiers
| Tier | Purpose | Typical modules |
|---|---|---|
| Tier 0 — Foundation | must exist before any business module | Organization (ORG), Security (SEC), Master Data Lookup (MDL) |
| Tier 1 — Core business | first revenue/cost flows | Procurement (PRC), Finance (FIN), Inventory (INV) |

A module may only declare a HARD-FK XM towards a module of the same or a lower tier.

## §2 Entity kinds and defaults
Entity kinds and their default fields are declared in `profiles/erp.yaml → conventions.entity_defaults`.
Rules the engines apply on top:
1. Every master entity is bilingual (`nameAr`, `nameEn`) and soft-deletable (`isActiveFl`).
2. Transactional documents are period-bound (`fiscalYearId`, `periodId`) and status-driven (`statusCode` from a lookup).
3. Lookups are owned by MDL; a module never stores a lookup's display text, only its code.
4. No entity generates its own document numbers — the platform numbering engine does.

## §3 Business-policy conventions (P0 → POL-*)
- A policy is a single, testable sentence in EARS form (see factory.yaml → ids.ears).
- Policies that cross modules are declared once, in the owning (lower-tier) module, and referenced by code elsewhere.
- Fiscal policies (period locking, posting rules) belong to FIN; approval-limit policies belong to the module that owns the document.

- Frontend: one lazily-loaded chunk per composite screen; Search↔Entry via route params.

## §5 Cross-module dependencies (XM)
- `HARD-FK`: a physical foreign key to another module's table — allowed only downward in tier.
- `SOFT-READ`: a read-only lookup by code — allowed in any direction.
- Every XM cites the `REQ-*` that needs it; the consuming module owns the XM record.
