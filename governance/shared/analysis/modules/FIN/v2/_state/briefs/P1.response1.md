The FIN v2 SRS delta (stage P1) is written, and `gov.py analyze -m FIN -v 2 --scope stage:P1` passes: 0 critical, 0 major, 71 minor. I haven't committed anything; the orchestrator does that. All 77 requirements, 83 acceptance criteria, 28 rules and 16 entities were actually checked, not skipped. Every story has at least one requirement except US-FIN-033, which the approved PRD defers.

**What the delta adds or changes** (numbering continues from v1):
- **New entities:**
  - ENT-FIN-015 **AccountMapping**: a mapping row picks one account for a given event type, business field and business value, has an active flag, and can be deactivated.
  - ENT-FIN-016 **RuleLineDimension**: a dimension tag whose value is either a constant or taken from a named business field in the event.
- **Changed entity:** ENT-FIN-010 RuleLine. DIRECT is gone and a new `accountBusinessFieldCode` field is added.
- **31 new requirements (REQ-FIN-047…077), 37 new acceptance criteria (AC-FIN-047…083) and 11 new rules (RULE-FIN-018…028)** cover stories US-FIN-020 to 032:
  - cheque goes to the bank account, cash to the cash account, and the expense account follows the expense type;
  - an event with no mapping for its value, or missing the business field, is rejected and nothing posts;
  - the mapping screen: add, search, change the account, deactivate, and a change never alters an entry already posted;
  - dimension tags are validated with the same checks as manual lines, and an event whose dimension value can't be resolved is rejected;
  - a duplicate event always gets the duplicate-event answer, and a non-open period gets its own answer.
- **Other v1 items changed:**
  - REQ-FIN-045 and AC-FIN-045: FIN now registers 15 lookup types instead of 13.
  - RULE-FIN-004: the duplicate answer now also covers the case where the database's uniqueness check catches it, which used to surface as a generic 500.
  - SCR-REQ-FIN-003 (engine rules) and SCR-REQ-FIN-006 (journal entries) updated to match.
- **New screen:** SCR-REQ-FIN-013, account mappings (page code `FIN_ACCOUNT_MAPPINGS`).
- **Five new decision records (ADR-FIN-023…027), all non-breaking.** The one worth reading is ADR-FIN-027. It keeps the existing v1 codes `FIN-409-DUPLICATE-EVENT` and `FIN-409-PERIOD-NOT-OPEN` unchanged, which confirms item §4 of the change request. It defines four new distinct errors (unmapped value, missing business field, unresolvable dimension value, no defined period) whose code names P3.1 will set. It also retires the v1 "MAPPING unsupported" code.

**Things you should know:**
- **I added lines to the root `v2/change-manifest.md`.** Its "Per artifact" section was empty, and that file is the only place the tools read the MODIFIED list from. P0 had written its manifest at `v2/P0/change-manifest.md`, which no tool reads. Without my addition, the six v1 items I changed would each have been a CRITICAL finding.
- **I restated some v1 content in full.** When `gov.py state` merges v2 over v1, it carries forward only the v1 blocks that have their own ID, and sections without IDs are dropped. So the SRS repeats v1's lookups, status lifecycles, dependencies, traceability rows and access notes, and the registry is a complete current registry rather than a delta.
- **The 71 minor findings are mostly old v1 content.** v1's acceptance criteria have no `Then :` label, and v1's RULE-FIN-008 uses the word "may". The new content produces only three:
  - ENT-FIN-010 and ENT-FIN-016 have no delete requirement. This is expected under ADR-FIN-025: dimension tags follow their rule line, which v1 made add-only.
  - US-FIN-029 (reports) has no "reject" requirement. I didn't invent one.
- **The design inherits a v1 gap.** A wrongly tagged rule line can only be retired by deactivating its rule, and v1 notes that deactivating a rule doesn't free its event type for a replacement.
- **What I ran and changed outside the deliverables:** I regenerated `_state/` so `analyze` had fresh input, and fixed one line in my restated text that the parser misread as a definition of `API-FIN-035`. The two modified P0.5 brief files in `git status` weren't touched by me.
