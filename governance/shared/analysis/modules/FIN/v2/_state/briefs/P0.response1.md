## OVERVIEW (MODIFIED — addendum)
يهدف الإصدار v2 من الحسابات العامة / Finance (General Ledger) (FIN) إلى تمكين FIN من اشتقاق
قيد اليومية / Journal Entry وترحيله / Posting انطلاقًا من الحدث المحاسبي القياسي / Canonical
accounting event الذي يُصدره نظام Oracle القديم، تمهيدًا لإيقاف المحاسبة في النظام القديم. يمرّ
هذا الانتقال بتشغيل متوازٍ (shadow mode) تُقارَن فيه قيود النظام القديم بقيود FIN سطرًا بسطر،
لذا يجب أن يحمل كل قيد مبني من حدث الحسابَ الصحيح وإسناد المؤسسة والفرع. الحد الحاكم لهذا الإصدار
هو القاعدة G6 نفسها: الحدث يصرّح بواقعة تجارية فقط، وFIN وحدها تقرر معناها المحاسبي؛ لا رمز حساب
ولا أي مفهوم محاسبي يعبر داخل حمولة الحدث. لا تتغير أي وحدة أخرى في المنصة بهذا الإصدار.

CLIENT-SPECIFIC POLICIES — ADDED

POL-FIN-021 — لا رمز حساب في حمولة الحدث / No account code in the event payload
  Statement : [en] The system shall derive every account of a journal entry built from a canonical accounting event without reading an account code from the event payload.
              [ar] يجب على النظام أن يشتق كل حساب في قيد اليومية المبني من حدث محاسبي قياسي دون قراءة أي رمز حساب من حمولة الحدث.
  Pattern   : ubiquitous
  Trigger   : Post (event)
  Rationale : الحدث يصرّح بواقعة تجارية وFIN وحدها تقرر معناها المحاسبي
  Source    : change manifest FIN v2 — الحد الحاكم + acceptance 1؛ domain-profile G6
  Status    : CONFIRMED

POL-FIN-022 — اشتقاق الحساب بالربط / Account derivation by mapping
  Statement : [en] When a rule line derives its account by mapping, the system shall resolve the account from the value of the named business field in the event through the FIN account mapping store for that event type.
              [ar] عندما يشتق سطر القاعدة حسابه بالربط، يجب على النظام أن يحدد الحساب من قيمة الحقل التجاري المسمّى في الحدث عبر مخزن ربط الحسابات في FIN لنوع الحدث ذاك.
  Pattern   : event
  Trigger   : Post (event)
  Rationale : النقد مقابل البنك حسب طريقة الدفع (11 من 16 فرعًا قديمًا) والحساب حسب نوع المصروف
  Source    : change manifest FIN v2 §1، acceptance 1
  Status    : CONFIRMED

POL-FIN-023 — التحقق من الحساب المُشتق بالربط / Mapped account validated like a constant one
  Statement : [en] When an account is resolved through the account mapping store, the system shall validate it as a leaf, active and postable account exactly as it validates an account given as a constant.
              [ar] عندما يُحدَّد حساب عبر مخزن ربط الحسابات، يجب على النظام أن يتحقق من أنه حساب ورقي ونشط وقابل للترحيل بالطريقة نفسها التي يتحقق بها من الحساب المُعطى كقيمة ثابتة.
  Pattern   : event
  Trigger   : Post (event)
  Rationale : المسار الجديد لا يفتح ثغرة في تحقق شجرة الحسابات
  Source    : change manifest FIN v2 §1
  Status    : CONFIRMED

POL-FIN-024 — رفض القيمة غير المربوطة / Unmapped business value rejected
  Statement : [en] If the business value carried by the event has no active account mapping for that event type and business field, then the system shall reject the event with a dedicated unmapped-value error and post no journal entry.
              [ar] إذا لم يكن للقيمة التجارية التي يحملها الحدث ربط حساب نشط لنوع الحدث والحقل التجاري ذاتهما، فعندئذٍ يجب على النظام أن يرفض الحدث بخطأ مخصّص للقيمة غير المربوطة وألّا يرحّل أي قيد يومية.
  Pattern   : unwanted
  Trigger   : Post (event)
  Rationale : لا قيمة افتراضية ولا تخمين أبدًا
  Source    : change manifest FIN v2 §1، acceptance 2
  Status    : CONFIRMED

POL-FIN-025 — الروابط بيانات لا شيفرة / Account mappings are data, not code
  Statement : [en] The system shall let authorised users add, change and deactivate account mappings as FIN-owned data through a FIN screen, without any code change.
              [ar] يجب على النظام أن يتيح للمستخدمين المخوَّلين إضافة روابط الحسابات وتعديلها وإيقافها كبيانات مملوكة لـ FIN عبر شاشة في FIN، دون أي تعديل في الشيفرة.
  Pattern   : ubiquitous
  Trigger   : Create / Update / Deactivate
  Rationale : كل ما يمكن أن يتغير بيانات مُعرَّفة، كسائر إعدادات FIN
  Source    : change manifest FIN v2 §1، acceptance 3؛ domain-profile G1
  Status    : CONFIRMED

POL-FIN-026 — وسوم الأبعاد على سطور القاعدة / Dimension tags on rule-driven lines
  Statement : [en] Where a rule line declares a value for a dimension, the system shall set that dimension on the journal line it builds from the rule's constant value or from the value of the named business field in the event.
              [ar] حيثما يصرّح سطر القاعدة بقيمة لبُعد ما، يجب على النظام أن يضبط ذلك البُعد على سطر القيد الذي يبنيه من القيمة الثابتة في القاعدة أو من قيمة الحقل التجاري المسمّى في الحدث.
  Pattern   : optional
  Trigger   : Post (event)
  Rationale : النظام القديم يختم المؤسسة والفرع على كل قيد؛ بدونها تفشل المقارنة المتوازية وتفرغ تقارير الأبعاد
  Source    : change manifest FIN v2 §2، acceptance 4
  Status    : CONFIRMED

POL-FIN-027 — التحقق من قيم الأبعاد المشتقة / Event-derived dimension values validated
  Statement : [en] When a dimension value is resolved for a journal line built from an event, the system shall validate that the value belongs to that dimension and is active, applying the same dimension rules as for a manually built line.
              [ar] عندما تُحدَّد قيمة بُعد لسطر قيد مبني من حدث، يجب على النظام أن يتحقق من أن القيمة تنتمي إلى ذلك البُعد وأنها نشطة، مطبّقًا قواعد الأبعاد نفسها المطبّقة على السطر المُدخل يدويًا.
  Pattern   : event
  Trigger   : Post (event)
  Rationale : تحقق الأبعاد القائم لا يُتجاوز
  Source    : change manifest FIN v2 §2
  Status    : CONFIRMED

POL-FIN-028 — رفض قيمة البُعد غير القابلة للتحديد / Unresolvable dimension value rejected
  Statement : [en] If a dimension value declared by a rule line is missing from the event or fails dimension validation, then the system shall reject the event and post no journal entry.
              [ar] إذا كانت قيمة البُعد التي يصرّح بها سطر القاعدة غائبة عن الحدث أو فشلت في التحقق، فعندئذٍ يجب على النظام أن يرفض الحدث وألّا يرحّل أي قيد يومية.
  Pattern   : unwanted
  Trigger   : Post (event)
  Rationale : القيد بلا إسناد فرع يُفسد المقارنة المتوازية كما يفسدها الحساب الخاطئ
  Source    : dialogue round 1 (resolved decision v2-2)؛ change manifest FIN v2 §2

## Round 1: proposals

PROPOSAL: Remove DIRECT account derivation. Dimension tags get their own two-value source mode.
  Affects   : RuleLine, the v1 account-derivation-mode lookup, FIN_DIMENSION_VALUE_SOURCE
  Options   : A) Remove DIRECT from account derivation. B) Deprecate it: existing DIRECT rules keep working and new ones are refused. C) Restrict it: allow DIRECT only for named event types or as the dimension source mode.
  Researched: DIRECT puts an account code in the payload, which goes against domain-profile G6 ("no account name inside the event payload") — a v1 rule. So v1 declared a mode its own governing rule forbids. Oracle Subledger Accounting reads an account from a source only when the subledger has already decided the account. The FIN architecture rules that out by design. Nothing from v1 was ever delivered (project-registry pipeline status: "deliver BLOCKED"), so no configuration data uses DIRECT and deprecating it protects nothing. Option C keeps one value that is valid for dimensions and invalid for accounts, and later validation stages would have to handle that ambiguity.
  Recommended: A. The dimension side uses FIN_DIMENSION_VALUE_SOURCE (constant / business field), so no label ever again means "account taken from the payload."
  Sources   : domain-profile G6, G1; change manifest §1; project-registry PIPELINE STATUS
  traces    : POL-FIN-021, POL-FIN-022

PROPOSAL: Reject the event and post nothing when a dimension value a rule line declares is missing or invalid.
  Affects   : RuleLineDimension, POL-FIN-028
  Options   : A) Reject the event (hard error, no entry). B) Post the line without that dimension and log a warning.
  Researched: The manifest says the existing validation "is not bypassed." Option B would produce entries with no branch, and those diverge in the parallel run in exactly the way the change set is meant to prevent. A hard error also matches the unmapped-account discipline in POL-FIN-024. A rule line that declares no dimension still produces a line without one, the same as a manual line.
  Recommended: A
  Sources   : change manifest §2 and its acceptance criteria; POL-FIN-024
  traces    : POL-FIN-027, POL-FIN-028

PROPOSAL: Defer translation of dimension values; only the two requested modes are in scope.
  Affects   : scope; AccountMapping (would widen it)
  Options   : A) Constant or named business field only; defer any translation. B) Widen the mapping store now so it can also resolve dimension values.
  Researched: The user asked for exactly two modes. Organisation and branch codes are business facts, not accounting concepts, so reading them directly stays within G6. Option B adds scope nobody requested.
  Recommended: A, deferred. Activation trigger: legacy organisation or branch codes turn out to differ from FIN dimension values.
  Sources   : change manifest §2; domain-profile G6
  traces    : POL-FIN-026

PROPOSAL: Business-field names come from a FIN-owned lookup registered in MDL.
  Affects   : lookups owned (FIN_EVENT_BUSINESS_FIELD), RuleLine, AccountMapping, RuleLineDimension
  Options   : A) Business-field names are values in the lookup. B) Free-text field names, checked only at post time.
  Researched: G1 says what can change is defined data. G4 and G5 place every coded list in the MDL hub, owned by the module that registers it. With free text, a typo only shows up when an event fails to post.
  Recommended: A. Initial values are the four the user named.
  Sources   : domain-profile G1, G4, G5; [KB:erp-domain-standards §2.3]
  traces    : POL-FIN-022, POL-FIN-026

PROPOSAL: One period-not-open code covers any existing period whose state refuses the posting. A date with no defined period is a configuration error.
  Affects   : POL-FIN-031; the error catalogue (named at P1/P3.1)
  Options   : A) One code for soft close, hard close and year-end close. B) Separate codes for reopenable and terminal states. C) Also use this code when no period exists for the date.
  Researched: The consumer needs one retryable signal distinct from validation and configuration errors (manifest §4). Separate codes per state are API detail for P3.1; the period state can travel with the response there. A missing period is a calendar-setup fault: opening a period does not fix it, so it belongs with configuration errors.
  Recommended: A, with C rejected.
  Sources   : change manifest §4; domain-profile §7.1 "الفترة المحاسبية / Accounting Period"
  traces    : POL-FIN-031
