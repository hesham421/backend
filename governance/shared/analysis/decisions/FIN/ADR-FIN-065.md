# ADR-FIN-065 — The frontend's consumer feedback is answered in the plan: owned-collection screens become list + record pages hydrated by a published `<entity>Pk` search, and eight binding gaps are closed
Status      : ACCEPTED (non-breaking)
Stage       : P3.2        Module: FIN        Version: v2
Lane        : analysis
Decided     : 2026-09-24
traces      : SCR-FIN-001, SCR-FIN-002, SCR-FIN-003, SCR-FIN-004, SCR-FIN-005, SCR-FIN-006, SCR-FIN-007, SCR-FIN-008, SCR-FIN-009, SCR-FIN-010, SCR-FIN-011, SCR-FIN-012, SCR-FIN-013, REQ-FIN-004, REQ-FIN-005, REQ-FIN-007, REQ-FIN-009, REQ-FIN-014, REQ-FIN-017, REQ-FIN-019, REQ-FIN-021, REQ-FIN-022, REQ-FIN-025, REQ-FIN-028, REQ-FIN-031, REQ-FIN-034, REQ-FIN-037, REQ-FIN-041, REQ-FIN-042, REQ-FIN-046, REQ-FIN-054

## Context

The frontend implementation of this plan (the mxdashboard FIN module) filed thirteen feedback records against
it, FB-1 … FB-13. The project owner has already decided the design questions they raise. This ADR records those
decisions and the plan edits that carry them. It re-opens none of them.

Every endpoint shape below was checked against `_inputs/api-docs-fin.md` as fetched for this stage. Every route
name was checked against the shipped `mxdashboard/src/App.tsx` and the feature `*RoutePaths.ts` files.

## Decision

### 1. Owned-collection screens are a list page and a record page (FB-1, FB-2, FB-7)

Owner decision, 2026-09-21. The rule sources are `erp-drawer-zustand` §11 and `ui-master-detail-records`.

Five screens hold a record that OWNS a child collection:

| Screen | Record → child collection | List | New | Record page | Cold-load read (published filter) |
|---|---|---|---|---|---|
| SCR-FIN-002 | dimension → values | `/fin/dimensions` | `/fin/dimensions/new` | `/fin/dimensions/:dimensionId` | API-FIN-005, `dimensionPk EQUALS` |
| SCR-FIN-003 | rule → lines | `/fin/rules` | `/fin/rules/new` | `/fin/rules/:ruleId` | API-FIN-009, `eventTypeRulePk EQUALS` |
| SCR-FIN-004 | template → lines | `/fin/recurring-templates` | `/fin/recurring-templates/new` | `/fin/recurring-templates/:templateId` | API-FIN-012, `recurringTemplatePk EQUALS` |
| SCR-FIN-005 | allocation rule → targets | `/fin/allocation-rules` | `/fin/allocation-rules/new` | `/fin/allocation-rules/:allocationRuleId` | API-FIN-015, `allocationRulePk EQUALS` |
| SCR-FIN-007 | fiscal year → periods | `/fin/periods` | `/fin/periods/new` | `/fin/periods/:fiscalYearId` | `POST /api/v1/fin/fiscal-years/search` (ADR-FIN-061), `fiscalYearPk EQUALS` |

The api-docs list each filter under that search's "Supported fields" as `(EQUALS, IN)`.

Each of the five screens has the same shape:
- **List page.** The whole viewport shows the list.
- **Record page.** The header form sits inline in a collapsible section with its own single submit. The child
  collection sits beneath it.
- **Child line add or edit.** A Drawer on its own search param: `?valueAction=create`, `?lineAction=create` or
  `?targetAction=create`.
- **`/new`.** Registered before `/:id`. After a save, the page moves to the record page, using the id from the
  CREATE RESPONSE.

Two screens have a published child write addressed by the parent's id: SCR-FIN-002 (API-FIN-007) and SCR-FIN-003
(API-FIN-011). On their `/new` pages the child section is locked and says why.

Two screens create the parent and its children in one call: SCR-FIN-004 (API-FIN-013) and SCR-FIN-005
(API-FIN-016). On their `/new` pages the children are composed in the line Drawer, and the one create sends them.
On their record pages the children are read-only, because no child write is published (ADR-FIN-006).

SCR-FIN-007's periods are generated by the year's create. On its record page they carry the transition row
actions.

**The cold-load read.** The record page hydrates on a cold deep link through the screen's PUBLISHED search, with
one filter, `<entity>Pk EQUALS <id>`, at page 0 and size 1. The search response carries the full aggregate. The
read is one F2 record hook per screen, under that screen's existing query-key root, so every invalidation the
plan already declares refreshes it. A zero-row answer renders an honest "not found" notice with a way back to the
list, never an empty form.

**ADR-FIN-006 narrows.** Its "no by-id read" stands for ENDPOINTS: no by-id endpoint is invented. A filtered
search is the record read.

**Not affected.** SCR-FIN-001 owns no child collection (a parent account is a reference, not an owned line; see
the ownership test in `ui-master-detail-records` §5), so it keeps Search + Entry Drawer. SCR-FIN-013 is a flat
record and keeps its Drawer too. SCR-FIN-006 already had `/new` and `/:id`. The report screens are unaffected
(ADR-FIN-003).

The ALIGN-FE operations-coverage table now names the record route for every write that lives on it, and names
the second role of the five searches.

### 2. SCR-FIN-006's fiscal-year select (FB-3)

The manual-entry form's year select is bound to the fiscal-year option read, `POST /api/v1/fin/fiscal-years/search`,
which is still cited by path (ADR-FIN-061). F2-SCR-FIN-006-FACADE now publishes the year options. Components still
read nothing except the facade.

The period select is narrowed client-side by `period.fiscalYearId`. The server's FIN-400-PERIOD-NOT-IN-YEAR and
FIN-400-DOCDATE-OUTSIDE-PERIOD remain the authority (RULE-FIN-017).

### 3. Balance sheet to trial balance drill-down (FB-4)

API-FIN-029 publishes exactly two query parameters, `periodId` and `accountTypeCode`. API-FIN-030 returns no
period. The drill therefore carries the row GROUP's `accountTypeCode` only, to
`/fin/reports/trial-balance?accountTypeCode=<code>`. It carries no account and no period. The flow diagram and
SCR-FIN-010's navigation say so.

The income-statement drill-down claimed the same two carriers and has the same defect: API-FIN-031 returns a
period range, while the trial balance takes one period. It is corrected the same way, to the group's
`accountTypeCode` only.

### 4. Income statement bounds (FB-5)

The api-docs publish `fromPeriodId` and `toPeriodId` on API-FIN-031 as independently optional, with no
cross-field rule. The filter schema and F2-SCR-FIN-011-FACADE send each bound that is set, on its own. They never
couple the two and never drop a half-specified range. An open-ended range ("from period 3") is a legal request.

### 5. Action affordances (FB-6, FB-12)

ADR-FIN-005 stands. There is no client-side action-level gating. No published endpoint carries the caller's
action-level permissions: the SEC effective menu (ADR-FIN-005) carries page codes only.

Every affordance renders for a caller who holds the screen. That includes CREATE, UPDATE, run, reverse, reopen,
hard-close and year-end-close. FIN-403-FORBIDDEN is the authority, and it is shown as the localized catalogue
message on the screen.

Removed from the plan:
- SEC-FE's "hidden without the grant" wording;
- the F4 Guard lines that made an affordance need CREATE, UPDATE or the Close-approve presence flag;
- the SCREEN-INIT rows that claimed an action-level permission read.

A data-state precondition is also left to the server. The year-end close renders enabled and shows a readiness
hint while periods are still open, and the server's FIN-409-PERIODS-NOT-CLOSED decides. The same holds for a
reopen after a hard close: FIN-409-NOT-REOPENABLE decides.

RULE-FIN-015's separation of duty is demonstrated by the server's 403, not by the screen. TC-FIN-082 step 2 and
TC-FIN-086 step 2 assert the gate this ADR removes. Test generation should align them at its next run. This
stage does not own them.

### 6. Nullable response fields (FB-8)

This is a plan-wide F1 rule. Every response field the api-docs mark as not required, or describe as null in some
case, is typed `T | null`, because the wire sends JSON `null`. It is never typed `?: T`. Presence tests use
`== null` / `!= null`, never `=== undefined`.

The rule is stated in PHASE F1's conventions and repeated in F1-SCR-FIN-003, F1-SCR-FIN-006 and F1-SCR-FIN-013.
The defect it prevents was live: a false "reversal" notice rendered on every entry, and the Reverse action was
permanently disabled.

### 7. Option reads (FB-13)

Every option read sends page 0 and size 200, the api-docs' maximum. Every option consumer discloses `hasMore`
(`totalElements > options.length`) when the set is capped, and it never truncates silently. That covers the
picker Drawers and also every plain `<select>`, including:
- the fiscal-year selects of SCR-FIN-010 and SCR-FIN-011;
- the year and period selects of SCR-FIN-006;
- SCR-FIN-013's selects.

Whether a required-filter select should become a searchable picker once its domain is unbounded is left open.
Disclosure is the rule today.

### 8. Event-rule business 409s (FB-10)

The republished api-docs bind FIN-409-RULE-DUP to API-FIN-010 and FIN-409-REMAINDER-COUNT to API-FIN-011, each
in that endpoint's Business Responses. SCR-FIN-003 binds both, inline:
- FIN-409-RULE-DUP on the rule Entry's eventTypeCode, with the message that an active rule already exists for the
  event type;
- FIN-409-REMAINDER-COUNT on the Line entry's remainder flag.

### 9. Journal-entry line refusals (FB-11)

FIN-409-NOT-POSTABLE-ACCOUNT and FIN-409-INVALID-DIMENSION on API-FIN-019 identify no line. `fieldErrors[].field`
carries the catalogue code, with no line index, line number, account id or dimension id. The plan binds each
refusal to the lines pane's refusal slot, announced exactly once. It never binds it to a guessed line.

**Known limitation.** AC-FIN-019 (offending line) and AC-FIN-021 (offending line and dimension) cannot be asserted
at line granularity until the backend publishes the offending line in `fieldErrors[].field`, and the dimension
code in `message` for FIN-409-INVALID-DIMENSION. This is a backend follow-up for P3.1's next delta.

### Out of scope: three app defects (FB-9)

FB-9 reports three implementation defects:
- a duplicate success toast on a heavy rule record;
- a stale previous entry rendered while record-to-record navigation loads;
- the FilterDrawer staying open over the grid it filtered.

None is a plan defect, and the plan already forbids each outcome. They are handed to the frontend's defect list.

## Consequences

- Non-breaking. No operation, field, rule, permission or endpoint is added or removed. The record read is a
  published search with a published filter.
- ADR-FIN-006 is narrowed, not superseded. It carries a note that points here.
- Changed: ui-ux-spec (SCR-FIN-002 … 007, 010, 011 and 013), flow diagram (the five master-detail flows and the
  two statement drill-downs), frontend plan (the F1 rule, the F2 record hooks and option rule, the F3 income
  bounds, the F4 routes and guards, the SEC-FE table and the ALIGN-FE route column) and the registry's ADR list.
  All of these were already MODIFIED in v2, so the change manifest's classifications do not change.
- Carried to other stages:
  - the backend follow-up on line-level refusals (§9);
  - the test-case alignment for TC-FIN-082 and TC-FIN-086 (§5);
  - P3.1 numbering the fiscal-year search (ADR-FIN-061).
