# ERP Backend

This is the **backend** repository. It contains Java source code, Maven build
configuration, API integration tests, and its own copy of the AI governance
content that applies to backend work.

> **Governance lives inside this repository.**
> All backend-relevant coding standards, architecture rules, and execution
> protocols live in `governance/` (this repo's own subfolder); the AI skills
> themselves live in `.claude/skills/` so they auto-load via the Skill tool —
> see "Workspace Layout" below for how this relates to `frontend/`.

## Where to Find Governance

This repository holds **no governance artifacts**. It knows two things: where
to read them, and where it may write. Both are the same place — the project
repository the governance factory publishes, mounted here as a submodule at
`governance/shared/`.

`git submodule update --init --recursive` after a clone, or none of the paths
below exist.

> **One tool reads the contract — never type a path.** `scripts/gov-module.py`
> reads every path and vocabulary from what the factory publishes
> (`governance/shared/platform/profile-summary.json → consumer`, schema 7, and
> `platform/modules-registry.json`). Every command and skill calls it:
> ```bash
> python3 scripts/gov-module.py pin                 # 0 = schema 7 · 3 = the project predates v7 (the factory owner runs gov.py upgrade-project) · 1 = refused
> python3 scripts/gov-module.py modules             # modules, build-order wave, delivered version
> python3 scripts/gov-module.py plan MOD [--json]   # plans, packages, tests, integration, API document, features, state file
> python3 scripts/gov-module.py requires MOD        # each integration package's `requires`, met or not
> python3 scripts/gov-module.py state-init MOD      # create/upgrade the execution state
> python3 scripts/gov-module.py record MOD …        # the ONLY writer of execution-state.json
> python3 scripts/gov-module.py validate [MOD]      # every execution-state file holds the contract (CI)
> python3 scripts/gov-module.py delivery MOD        # per-package acceptance — the progress report
> ```
> The module's version is the **delivered** version from the registry (`plan`),
> never the highest `analysis/modules/MOD/vN` folder — a delta `vN` holds only
> what changed.

### What this repo READS (never writes)

| What | Where (`plan --json` field) |
|---|---|
| Rules every runtime follows, skill routing, convention precedence | `governance/shared/platform/rules/GOVERNANCE-RULES.md` (when the project publishes it) |
| Modules registry, build order, dependency graph, factory pin | `governance/shared/platform/` |
| A module's published contract | `governance/shared/platform/contracts/contract-<mod>.md` (`contract`) |
| A module's analysis — PRD, SRS, db-script, plans, feature prompts | `governance/shared/analysis/modules/<MOD>/` (`exec_plan` P3.1, `test_plan` P4, `features`) |
| The delivered packages (factory-written) | `governance/shared/backend/modules/<MOD>/packages/` (`exec_packages`, `test_packages`, `exec_units`, `test_units`, `integration`; `…/packages/vN/…` for a delta version) |
| The API document — the API contract (OpenAPI 3.1) | `governance/shared/backend/modules/<MOD>/packages/api-spec-<mod>.yaml` (`api_spec`) |
| Decision records a plan cites | `governance/shared/analysis/decisions/<MOD>/` |

Plans carry their facts in NAMED yaml blocks (```` ```yaml name=<block> ````):
`error-catalog`, `permission-matrix`, `bootstrap`, `totals`, `self-check`, …;
a db-script's DDL is ONE ```` ```sql ```` fence and its field matrix the
`dbf-matrix` block (`id, table, column, type, entity_field, traces`). Read the
named block, never a prose table.

### What this repo WRITES (its own partition, and nowhere else)

Only under `governance/shared/backend/modules/<MOD>/` — and never its
`packages/` (the factory's delivery), never `analysis/`:

| What | Where |
|---|---|
| Execution state — the feedback channels and delivery rows | `backend/modules/<MOD>/execution-state.json` (`state_file`) — written only by `gov-module.py record` |
| API documentation, generated from the running app | `backend/modules/<MOD>/api-docs/` (`index.md`, then `**/*.md`) |
| API verification script and problems report | `backend/modules/<MOD>/test-api/` |

`./scripts/governance push` stages only this track's pathspec
(`gov-module.py pathspec`), so anything written elsewhere is not published.
The frontend's partition and the factory's are not this repo's to touch.

### Start and end of work

```bash
./scripts/governance pull                      # start: the factory's latest, the pin check, the derived sparse scope
python3 scripts/gov-module.py validate MOD     # end: the state file holds the contract
./scripts/governance push                      # end: publish this track's partition, commit the pointer
./scripts/governance status                    # where this repo stands
```

Use them instead of raw `git submodule` calls. `git submodule update` leaves the
shared checkout on a **detached HEAD**, and a commit made there is referenced by
nothing: the next update walks away from it and the push that should publish it
succeeds publishing nothing. The script checks for that and says so.

### The review gate

The factory runs ONE review gate per module, `analysis` (after P4), and splits
packages only after it. If `gov-module.py plan MOD` refuses with *"no backend
delivery yet"*, the module is not ready for this repo — there is nothing to build.

### The feedback contract — record it, do not patch it

The plan is the factory's to write. What you discover while implementing goes
into **this repo's own partition** through `gov-module.py record`, and the
factory reads it (`gov.py feedback`) and answers it (`gov.py answer-feedback`).

| Row | Command | When |
|---|---|---|
| `package_results` | `record MOD package UNIT --passed N --failed N` | after building/testing each unit — accepted when its listed tests are green (`tests-green`); a `no_tests` unit records `0/0` after a clean build |
| `features_done` | `record MOD feature FEAT-MOD-NNN` | after executing a feature prompt (`plan.features`) |
| `api_verify` | `record MOD api_verify --version <delivered_version> --result PASS\|FAIL` | after api-verify; the frontend's delivery stays OPEN until it is PASS |
| `api_doc_gaps` (key `endpoint`) | `record MOD api_doc_gaps --key "<METHOD> <path>" --resolution "OPEN — …" [--detail …]` | the plan / API document is wrong or silent |
| `blocked` (key `id`) | `record MOD blocked --key OQ-… --resolution "OPEN — …"` | an OQ or decision blocks a task |
| `deferred_xm` (key `id`) | `record MOD deferred_xm --key XM-… --resolution "DEFERRED — <requires> not met"` | an integration package whose `requires` is not met |

A `resolution` must **start with a declared word** — OPEN / DEFERRED / PENDING
(the factory owes an answer) · RESOLVED / CLOSED / IMPLEMENTED (settled in code)
· HUMAN / ADR (needs a decision). The tool refuses anything else ("blocked
pending …" is not a resolution); re-recording the same key replaces the row,
which is how a gap is closed. `xm_events` is the factory's channel — never
written here.

### What stays here (tools and reports, not governance)

| What | Where |
|---|---|
| Backend skills | `.claude/skills/` |
| AI commands | `.claude/commands/` (not under `governance/` — moved 2026-09-05 so slash commands auto-load, same reason skills moved) |
| api-doc-generator and other tooling | `governance/governance-tools/` |
| Postgres MCP (DB inspection, read-only) | wired in `.mcp.json` as `postgres` (`postgres-mcp`, `--access-mode=restricted`); self-hosted reference copy at `governance/mcp-servers/postgres/` |
| Reporting / non-impacting markdown (see below) | `governance/project-artifacts/` |
| TestSprite (RETIRED as the backend test mechanism — history only; `api-verify` replaced it) | `governance/testsprite/` |

## Phase Execution Protocol

> Applies when executing a module's delivered packages. This section governs
> HOW to execute — the skill routing table in `GOVERNANCE-RULES.md` governs WHAT
> to use. `/orchestrate-module` is the full protocol; this is its summary.

### Entry
1. `./scripts/governance pull`, `python3 scripts/gov-module.py pin` (exit 3 → stop: the factory owner runs `gov.py upgrade-project`).
2. `python3 scripts/gov-module.py plan [MODULE] --json` and `state-init [MODULE]`.
3. `python3 scripts/gov-module.py delivery [MODULE]` — the first unit not `accepted` is where work resumes.

### Order
1. The exec phases in `plan.phases` order, skipping the phase with
   `integration: true`; a phase's units are its `exec_units` (each a
   `{unit}.package.json` + `{unit}.md`). No phase name or position is fixed.
2. Each XM edge is ONE integration package (`plan.integration`): built only
   when `requires_met`, otherwise recorded as `deferred_xm`. Integration
   packages are excluded from the module's own delivery.
3. Feature prompts not `done` (`plan.features`), then `record … feature`.
4. Test units, api-docs publication, api-verify → the `api_verify` row.

### Per unit
1. Read the unit's `.md` completely, its phase `*-HEADER.md`, the named blocks it
   cites, its operations in the API document (`plan.api_spec`), the db-script's
   `sql` fence / `dbf-matrix`.
2. Map each task to the skill routing table; read the skills from `.claude/skills/`.
3. Execute all tasks in order; write and run the unit's acceptance tests (its manifest's `tests`).
4. Run `gov-validate-backend-feature`.
5. `python3 scripts/gov-module.py record [MODULE] package [UNIT] --passed N --failed N`.

### Blocked items — OQ / XM deferred
- OQ-blocked task → skip, mark in code `// TODO: OQ-[ID] — pending resolution`,
  `record [MODULE] blocked --key OQ-[ID] --resolution "OPEN — …"`.
- Integration package not met → `record [MODULE] deferred_xm --key XM-… --resolution "DEFERRED — <requires> not met"`.
- Continue remaining tasks — never stop the phase for a blocked item.

### Exit
`python3 scripts/gov-module.py validate [MODULE]`, then `./scripts/governance push`.
Print units accepted / failing, blocked, deferred XM, gaps, next unit — and wait
for the user before the next phase.

### Constraints (NON-NEGOTIABLE)

- NEVER skip a unit within a phase
- NEVER invent field or column names — the db-script's `dbf-matrix` block and `sql` fence are ground truth
- NEVER invent an endpoint, status or error code — the API document is the contract
- NEVER copy QRC entries as production code — read intent, write implementation
- NEVER implement a blocked OQ item — mark and skip only
- NEVER hand-edit `execution-state.json` — `gov-module.py record` only
- NEVER advance to next phase without explicit instruction from user

## Legacy Module Path

Modules on this path: **CU, NOTIF, FILE** (backend-complete,
built under the pre-split model — `P0`/`P1`/`P2`/`P3`/`P3_5`/`P4` combined,
`packages/execution/` combined, rather than the current
`P0`/`P0_5`/`P1`/`P2`/`P2_5`/`P3_1`/`P3_5_BE` split and
`packages/backend-execution/`). These three were once called ORG,
NOTIFICATION and FILESVC; the packages are `com.erp.cu`, `com.erp.notif`
and `com.erp.file` today — search for the current names, the old ones
resolve to nothing. **SEC** (formerly SECURITY) **is explicitly NOT on
this path** and Legacy Path logic must never be applied to it — see
criterion 3 below.

The migration history under `src/main/resources/db/migration/` contains
create-then-drop pairs for modules that no longer exist; those files are
immutable applied records, not a description of live schema, so encountering
one is never a reason to resurrect anything.

A module qualifies for the Legacy Path if ALL of the following hold:
1. It has real, working backend code already implemented.
2. Its `governance/shared/analysis/modules/<MOD>/` folder predates the current governance
   model — combined `P3`/`P3_5`/`P4` naming, OR missing formal
   `P0_5`/`P2_5`/`P3_1` artifacts entirely.
3. It is not SEC (formerly SECURITY).

A Legacy Path module:
- Keeps its existing `governance/shared/analysis/modules/<MOD>/` structure **untouched** —
  no retroactive rename of `P3`→`P3_1`, `P3_5`→`P3_5_BE`, or
  `packages/execution/`→`packages/backend-execution/`. This is a
  deliberate, already-made decision — do not revisit it.
- Gets metadata-level fixes only where something is simply wrong (a
  misnamed folder, a missing registry entry) — never a structural
  migration. Fixing a naming mistake is not the same as retroactively
  migrating a legacy structure; the two must never be conflated.

## Running Locally

**Requires JDK 25.** `pom.xml` pins `java.version`/`maven.compiler.release` to 25 and a
`maven-enforcer-plugin` rule fails the build immediately (at `validate`, before any compilation)
under any other JDK, with a message naming the JDK actually in use. Point `JAVA_HOME` at a JDK 25
install before running any `mvn` command below.

```bash
# Start Postgres + Redis (named volumes — survives `docker compose down` and
# machine reboots; only an explicit `down -v` deletes the data)
docker compose --env-file .env -f docker/docker-compose.yml up -d

# Build and run the Spring Boot application (single module — no -pl needed;
# mainClass is configured to com.erp.main.ErpMainApplication in pom.xml)
mvn spring-boot:run

# Or run the PowerShell test runner directly
powershell -ExecutionPolicy Bypass -File tests/masterdata-api-test.ps1
```

Copy `.env.example` to `.env` and fill in values before running locally (`.env` is gitignored —
never commit real secrets). `--env-file .env` points `docker/docker-compose.yml`'s variable
substitution at that same root `.env` — no separate docker-specific env file to keep in sync,
and unlike a service-level `env_file:` it does not inject the whole `.env` (JWT_SECRET,
MAIL_PASSWORD, etc.) into the Postgres/Redis containers. Default credentials
(`postgres`/`postgres`/`erp_db` on port 5432, Redis on 6379) match `application-dev.properties`'
own fallbacks, so it works with zero `.env` changes for a first run. **Never run
`docker compose down -v`** unless you actually mean to delete the database — plain `down`, a
container restart, or a full machine reboot all preserve the named volumes.

`.mcp.json`'s `DATABASE_URI` and TestSprite `API_KEY` use `${VAR}` substitution, which Claude
Code resolves from its own process environment — **not** by auto-loading `.env`. Export the
values from `.env` into your shell before launching Claude Code, e.g.
`set -a && source .env && set +a`, or export them individually
(`DB_USERNAME`, `DB_PASSWORD`, `DB_NAME`, `TESTSPRITE_API_KEY`).

These carry no functional value in this repo. Delete them on sight instead of

## Database Migration Policy (Flyway)

Schema changes are managed by Flyway (`org.flywaydb:flyway-core` +
`flyway-database-postgresql` in `pom.xml`) and applied automatically on
startup by Spring Boot's `FlywayAutoConfiguration` — never invoked manually
unless explicitly debugging (`mvn flyway:migrate` is wired but inert
otherwise).

- **Location**: `src/main/resources/db/migration/`
- **Naming**: `V<N>__<snake_case_description>.sql` — `N` is a strictly
  sequential integer with no gaps or reuse. **Never write a specific version
  number into this document or carry one from memory** — it drifts the moment
  the next migration lands. Instead, derive the next number at creation time by
  inspecting the migration directory, e.g.
  `ls src/main/resources/db/migration/ | grep -oE '^V[0-9]+' | sort -t V -k2 -n | tail -1`
  gives the current highest `V<N>`; the next file is `V<N+1>`.
- **NEVER edit a migration file that has already been merged/applied.**
  Flyway checksums applied migrations; editing one breaks every environment
  that already ran it. A wrong or outdated migration is corrected by adding
  a new migration that fixes it forward — not by rewriting history.
- **One logical schema change per file** (a table + its seed data, or a
  single reconciliation fix) — mirror the granularity of whatever migrations
  already exist in `src/main/resources/db/migration/` (open that directory to
  see the current set), not one giant file per module and not one file per
  column.
- Table/column naming inside migrations follows the same `build-create-entity`
  skill conventions (UPPER_SNAKE_CASE, module prefix) — a migration and its
  matching JPA entity must agree on the physical name.

### If you are about to do X, the answer is always Y

- **About to add a new backend execution-plan phase file, JUnit scenario, or a generated `execute-backend*.md` command?** → `backend/governance/`. Never `frontend/governance/`.
- **About to add a new Playwright scenario, frontend skill, or a generated `execute-frontend*.md` command?** → `frontend/governance/`. Never `backend/governance/`.
- **About to edit `governance-tools/*.py`?** → Backend-only; edit it in `backend/governance/governance-tools/`. Do not assume a change here needs mirroring into `frontend/governance/` — its tooling is a separate, independently maintained copy.
- **About to edit `.claude/commands/generate-module-setup.md` or any generated `[MODULE]/execute-backend*.md`?** → Backend-only; edit it in `backend/.claude/commands/` (repo root, not `backend/governance/` — moved 2026-09-05). Do not assume a change here needs mirroring into `frontend/governance/.claude/commands/` — its tooling is a separate, independently maintained copy.
- **About to write a report, investigation note, or audit writeup?** → `governance/project-artifacts/`. Never the root of `governance/`, never inside `modules/`.
- **About to run TestSprite?** → Don't: it is retired. API verification is the `api-verify` skill (the published api-docs held to the API document), recorded with `gov-module.py record MOD api_verify`.
- **Found yourself wanting to copy a NEW file from `backend/` into `frontend/` (or vice versa) that isn't already an established dual-copy pattern (the Playwright MCP server)?** → STOP. This requires an explicit human decision, not silent duplication. Ask first.
- **About to regenerate frontend package content (`packages/frontend-execution/`, `packages/frontend-test/`) from this repo?** → Not possible by design. `agent3_splitter.py` in this repo only ever knows the backend and only runs meaningfully against this repo's own artifacts — there's nothing here to regenerate frontend content from.
- **About to edit `execution-state.json`?** → Only through `python3 scripts/gov-module.py record` (and `state-init`). A hand edit is how a resolution word the factory cannot read gets in.

### No new top-level content categories without explicit confirmation

Do not create a new folder type, a new cross-repo dependency, or a new
"shared" location under either `governance/` tree without first producing
a short written justification and getting explicit human confirmation.
Never skip straight to implementation.

There is no longer any exception: the last one (`shared/modules-registry.json`
at the project root, outside both `governance/` trees) was removed 2026-09-12.
Every repo now reads only paths inside itself, and anything two repos must agree
on is written into each of them by the governance factory (`gov.py publish`).

### Decision authority

This structure was deliberately designed to keep `backend/` and `frontend/`
independently workable without opening the other. Any deviation — new
duplication, new cross-repo path reference, new shared location — requires
evidence-based analysis, a dry-run plan, and explicit human confirmation.
Silent structural drift is treated as a governance violation, not a
convenience.
